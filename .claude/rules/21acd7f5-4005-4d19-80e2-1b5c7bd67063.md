<rule_activation id="21acd7f5-4005-4d19-80e2-1b5c7bd67063" title="Enforce Input Validation and Boundary Checking for Configuration Parameters: Configuration Parameters Received" applies_to="**/*">
These rules are ALWAYS ACTIVE for all runtime configuration and environment management code. All configuration parameter handling MUST comply with the input validation rules defined herein.
</rule_activation>

### Rules

- **R-CFG-001** MUST: All configuration parameters received from external sources (environment variables, API requests, file system, user input) MUST be validated before use.
- **R-CFG-002** MUST: Validate environment variable processing and parsing.
- **R-CFG-003** MUST: Validate API request parameter validation.
- **R-CFG-004** MUST: Validate user input from forms and interactive elements.
- **R-CFG-005** MUST: Validate configuration file parsing (JSON, YAML, TOML, etc.).
- **R-CFG-006** MUST: Validate query string and URL parameter handling.
- **R-CFG-007** MUST: Validate runtime feature flags and toggles.
- **R-CFG-008** MUST: Validate resource limits and thresholds (memory, timeouts, sizes).
- **R-CFG-009** SHOULD: Use schema validation libraries (Zod, Yup, Joi) to define configuration schemas declaratively and generate TypeScript types from schemas.
- **R-CFG-010** SHOULD: Implement validation at the earliest possible point in the data flow, ideally immediately after reading from external sources.
- **R-CFG-011** SHOULD: Provide clear, actionable error messages that include the parameter name, received value, expected format, and valid range.
- **R-CFG-012** SHOULD: Cache validated configuration values to avoid repeated validation overhead, especially for environment variables that don't change during runtime.
- **R-CFG-013** SHOULD: Log validation failures with appropriate severity levels to enable monitoring and alerting on configuration issues.

### Verify

```bash
# Check for unvalidated environment variable access
grep -r 'process\.env\[' --include='*.ts' --include='*.tsx' --include='*.js' | grep -v 'validate\|check\|parse' | wc -l

# Check for unvalidated numeric parsing operations
grep -r 'parseInt\|parseFloat\|Number(' --include='*.ts' --include='*.tsx' | grep -v 'isNaN\|isFinite\|>\|<\|throw' | head -20

# Run validation and configuration tests
npm test -- --grep 'validation|config' || echo 'No validation tests found'
```

**Accept when:**
- All direct accesses to process.env are wrapped in validation functions that check type and range
- Numeric parsing operations (parseInt, parseFloat, Number) are followed by boundary checks or NaN/Infinity validation
- Test suite includes validation test cases for configuration parameters covering valid, invalid, and edge case inputs
- Configuration parameters from external sources are validated before use in the application
- Validation logic includes clear error messages with parameter name, received value, expected format, and valid range

<enforcement>
Claude Code MUST NOT skip or defer verification. All configuration parameter handling MUST comply with these rules. Violations detected by static analysis tools, code review, or security scanning MUST be addressed before merge. Exceptions require explicit documentation, tech lead approval, and security review for production code.
</enforcement>
