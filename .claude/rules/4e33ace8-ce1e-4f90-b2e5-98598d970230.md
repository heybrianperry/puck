<rule_activation id="4e33ace8-ce1e-4f90-b2e5-98598d970230" title="Standardize Message Queue Integration for Public API Event Distribution: Event Payloads Published" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching public-facing REST APIs, external webhook receivers, GraphQL mutations, and API gateway integration points that trigger state changes.
</rule_activation>

### Rules

- **R-MQ-001** MUST: Event payloads published to message queues MUST include sufficient context for downstream consumers to process independently

### Scope

**In scope:**
- All public-facing REST APIs that trigger state changes
- External webhook receivers that initiate internal workflows
- GraphQL mutations that require asynchronous processing
- API gateway integration points with internal services

**Out of scope:**
- Internal service-to-service communication within the same bounded context
- Synchronous read operations and queries
- Administrative APIs used exclusively by internal tooling
- Real-time streaming APIs using WebSocket or SSE protocols

**Exceptions:**
- EXC-001: API operations require immediate synchronous validation from downstream services that cannot be deferred
- EXC-002: Legacy APIs undergoing gradual migration where immediate refactoring would disrupt existing integrations

### Verify

```bash
# Detect direct service invocations in API layer
grep -r "publish.*Event\|sendMessage\|enqueue" packages/*/src/api --include="*.ts" | grep -v test

# Verify message queue abstraction imports
grep -r "import.*MessageQueue\|import.*EventBus" packages/core packages/tsup-config --include="*.ts"

# Count synchronous service calls in API layer
find . -name "*.ts" -path "*/api/*" -exec grep -l "await.*service\." {} \; | wc -l
```

**Accept when:**
- All public API endpoints that trigger state changes publish events to message queues rather than making direct service calls
- Message queue integration code is located in API boundary layers (controllers, resolvers) and not in core domain services
- Event schemas are documented with version numbers and backward compatibility is maintained across versions
- Event payloads include sufficient context (domain, entity, action, timestamp, correlation IDs) for independent downstream processing
- Idempotency keys are present in event payloads to handle duplicate message delivery
- Queue naming follows conventions (e.g., api.{domain}.{entity}.{action})
- Dead letter queues are configured for failed message handling

<enforcement>
Claude Code MUST NOT skip or defer verification of message queue integration patterns in public API layers. All state-changing API operations MUST be verified to publish events asynchronously rather than making direct synchronous service calls. Violations MUST be flagged for architecture review before approval.
</enforcement>
