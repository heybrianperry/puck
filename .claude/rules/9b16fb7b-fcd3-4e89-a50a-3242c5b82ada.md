<rule_activation id="9b16fb7b-fcd3-4e89-a50a-3242c5b82ada" title="Standardize Environment Variable Configuration for Runtime Execution Context: Environment Configuration Access" applies_to="**/*">
These rules are ALWAYS ACTIVE for all runtime environment and configuration management implementations across the codebase.
</rule_activation>

### Rules

- **R-ENV-001** MUST: Environment configuration access patterns MUST be consistent across all framework implementations (Remix, Next.js) within the codebase.
- **R-ENV-002** MUST: All server-side route handlers and API endpoints MUST use centralized configuration modules for environment variable access.
- **R-ENV-003** MUST: Data access layers and model files (*.server.ts) MUST access environment variables through centralized configuration modules.
- **R-ENV-004** MUST: Application initialization and bootstrap code MUST validate all required environment variables at startup and fail fast with clear error messages.
- **R-ENV-005** MUST: Client-side hooks requiring runtime configuration MUST use framework-specific safe patterns (NEXT_PUBLIC_ prefix in Next.js, *.server.ts in Remix).
- **R-ENV-006** MUST: No hardcoded URLs, API keys, or credentials are permitted in application code outside of example/test files.
- **R-ENV-007** MUST: Server-side environment variables MUST NOT be exposed to client-side code.
- **R-ENV-008** SHOULD: Create centralized configuration modules (e.g., config.server.ts) that validate and export all environment variables with proper TypeScript types.
- **R-ENV-009** SHOULD: Maintain .env.example files in version control documenting all required and optional environment variables with descriptions and example values.
- **R-ENV-010** SHOULD: Implement framework-specific patterns: use *.server.ts suffix in Remix for server-only code, use NEXT_PUBLIC_ prefix in Next.js for client-accessible variables.

### Verify

```bash
# Check for direct process.env access outside config modules
grep -r 'process\.env\.' --include='*.ts' --include='*.tsx' | grep -v '\.server\.' | grep -v 'NEXT_PUBLIC_' | grep -v 'config\.' || echo 'No direct process.env access found outside config modules'

# Count configuration modules with environment variable access
find . -name '*.server.ts' -o -name 'config.ts' | xargs grep -l 'process\.env' | wc -l

# Check for hardcoded URLs, API keys, or credentials
grep -r 'const.*=.*['\'"](http|https|api|key|secret|password)' --include='*.ts' --include='*.tsx' | grep -v 'test' | grep -v 'example' || echo 'No hardcoded URLs found'
```

**Accept when:**
- All environment variable access is centralized in configuration modules or uses framework-specific safe patterns (*.server.ts, NEXT_PUBLIC_ prefix)
- No hardcoded URLs, API keys, or credentials are found in application code outside of example/test files
- Application startup includes validation that fails fast with clear error messages when required environment variables are missing
- .env.example file exists documenting all required and optional environment variables
- No direct process.env access is detected outside approved configuration modules
