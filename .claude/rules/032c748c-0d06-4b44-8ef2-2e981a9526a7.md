<rule_activation id="032c748c-0d06-4b44-8ef2-2e981a9526a7" title="Adopt Event-Driven Synchronization for State Management in Integration Boundaries: State Synchronization Implementations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files at integration boundaries, particularly in components that manage external state or coordinate with external systems.
</rule_activation>

### Rules

- **R-EVDS-001** MUST: State synchronization implementations MUST handle asynchronous updates and provide mechanisms to reconcile state differences.

### Verify

```bash
# Identify event-driven synchronization patterns with hooks or event listeners
grep -r "use.*[Ss]ync" --include="*.ts" --include="*.tsx" --include="*.js" | grep -E "(hook|event|subscribe)"

# Count event listeners and subscriptions across codebase
grep -r "addEventListener\|on(.*\)\|subscribe" --include="*.ts" --include="*.tsx" --include="*.js" | wc -l

# Find files implementing event-driven synchronization patterns
find . -type f \( -name "*.ts" -o -name "*.tsx" -o -name "*.js" \) -exec grep -l "event.*sync\|sync.*event" {} \;
```

**Accept when:**
- Grep commands identify at least 2 files implementing event-driven synchronization patterns with hooks or event listeners
- Code review confirms that integration boundaries use event-driven patterns rather than direct synchronous coupling
- No new direct synchronous state coupling is introduced at integration boundaries without architectural review approval

<enforcement>
Claude Code MUST NOT skip or defer verification. Automated code analysis in CI pipeline scanning for event-driven patterns at integration boundaries is mandatory. Architecture review is required for new integration points and API boundaries. Violations trigger CI pipeline warnings and require architecture team assessment.
</enforcement>
