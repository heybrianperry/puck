<rule_activation id="31dde3c0-5900-47c0-bf41-f0d238afd1ec" title="Adopt Event-Driven Synchronization for State Management in Integration Boundaries: Implementations Use Debouncing" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching integration boundaries, rich text editors, changelog generation scripts, API integration layers, and state management utilities that coordinate across architectural boundaries.
</rule_activation>

### Rules

- **R-EVDS-001** MAY: Implementations MAY use debouncing, throttling, or batching strategies to optimize event processing performance

### Verify

```bash
# Identify event-driven synchronization patterns with hooks or event listeners
grep -r "use.*[Ss]ync" --include="*.ts" --include="*.tsx" --include="*.js" | grep -E "(hook|event|subscribe)"

# Count event listeners and subscriptions across codebase
grep -r "addEventListener\|on(.*\)\|subscribe" --include="*.ts" --include="*.tsx" --include="*.js" | wc -l

# Find files implementing event-driven synchronization patterns
find . -type f \( -name "*.ts" -o -name "*.tsx" -o -name "*.js" \) -exec grep -l "event.*sync\|sync.*event" {} \;
```

**Accept when:**
- Grep commands identify at least 2 files implementing event-driven synchronization patterns with hooks or event listeners
- Code review confirms that integration boundaries use event-driven patterns rather than direct synchronous coupling
- No new direct synchronous state coupling is introduced at integration boundaries without architectural review approval
- Debouncing, throttling, or batching strategies are documented where event processing performance optimization is applied

<enforcement>
Claude Code MUST verify event-driven synchronization patterns at integration boundaries. Violations require architecture review approval before proceeding. Technical debt tickets MUST be created for existing violations. Exception requests MUST include performance justification and monitoring plans.
</enforcement>
