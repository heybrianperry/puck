<rule_activation id="39d291fc-d58a-412d-9a5c-06037884d659" title="Adopt Explicit Export Pattern for Library Module Public APIs: Utility Functions Data" applies_to="packages/core/lib/**/*.ts,packages/core/lib/**/*.tsx,packages/core/components/**/*.ts,packages/core/components/**/*.tsx">
These rules are ALWAYS ACTIVE for all public-facing modules under packages/core/lib and packages/core/components to establish explicit export patterns and maintain clear public API boundaries.
</rule_activation>

### Rules

- **R-EXP-001** MUST: Utility functions and data transformation modules MUST be self-contained with no side effects at module load time.
- **R-EXP-002** MUST: All public-facing modules under packages/core/lib and packages/core/components MUST have explicit export statements.
- **R-EXP-003** MUST: Internal helper functions and private utilities MUST NOT be exported from public API modules.
- **R-EXP-004** MUST: Server-specific modules MUST use .server.tsx extension and MUST NOT be imported in client-side code.
- **R-EXP-005** MUST: Package.json exports field MUST restrict access to only intended public modules.
- **R-EXP-006** SHOULD: Use TypeScript's 'export type' for type-only exports to prevent runtime inclusion in bundles.
- **R-EXP-007** SHOULD: Establish naming conventions with index.tsx for component exports and descriptive names for utilities (e.g., flatten-data.ts, populate-ids.ts).
- **R-EXP-008** SHOULD: Document public APIs in a centralized API reference, generated from TSDoc comments on exported members.
- **R-EXP-009** MAY: Use API Extractor or similar tools to generate API reports and detect unintentional breaking changes.

### Verify

```bash
# Count explicit export statements in public modules
grep -r 'export {' packages/core/lib packages/core/components | wc -l

# Find all index files that serve as module entry points
find packages/core -name 'index.tsx' -o -name 'index.ts' | wc -l

# Run API Extractor to check public API surface
npx api-extractor run --local || echo 'API surface check'

# Verify server-specific modules use correct naming convention
grep -r '\.server\.' packages/core/components | grep -v node_modules
```

**Accept when:**
- All public-facing modules under packages/core/lib and packages/core/components have explicit export statements
- No internal helper functions or private utilities are exported from public API modules
- Server-specific modules use .server.tsx extension and are not imported in client-side code
- Package.json exports field restricts access to only intended public modules
- API Extractor runs successfully without detecting unintended breaking changes
- No side effects occur at module load time in utility and data transformation modules
