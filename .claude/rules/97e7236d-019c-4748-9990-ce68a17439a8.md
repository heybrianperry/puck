<rule_activation id="97e7236d-019c-4748-9990-ce68a17439a8" title="Standardize Environment Variable Access via process.env for Runtime Configuration: Applications Use Environment" applies_to="**/*">
These rules are ALWAYS ACTIVE for all runtime configuration and environment management implementations across the codebase.
</rule_activation>

### Rules

- **R-ENV-001** MAY: Applications MAY use environment variable validation libraries (e.g., zod, envalid) to enforce configuration schemas.
- **R-ENV-002** MUST: All server-side runtime configuration (API endpoints, database URLs, service credentials) MUST be accessed via process.env.
- **R-ENV-003** MUST: Feature flags and environment-specific behavior toggles MUST be accessed via process.env.
- **R-ENV-004** MUST: Build-time configuration that varies across deployment targets MUST be accessed via process.env.
- **R-ENV-005** MUST: Third-party service integration parameters (API keys, webhook URLs) MUST be accessed via process.env.
- **R-ENV-006** MUST: Application-level settings (port numbers, timeouts, resource limits) MUST be accessed via process.env.
- **R-ENV-007** MUST NOT: Static configuration that never changes across environments (e.g., application constants, algorithm parameters) MUST NOT use process.env.
- **R-ENV-008** MUST NOT: Client-side only configuration in browser environments where process.env is not available MUST NOT rely on process.env directly.
- **R-ENV-009** MAY: Client-side code in Next.js MAY access NEXT_PUBLIC_* prefixed environment variables that are explicitly intended for browser exposure.
- **R-ENV-010** MAY: Test environments MAY use hardcoded configuration values when testing configuration validation logic itself.
- **R-ENV-011** MUST: A centralized configuration module that reads from process.env and exports typed configuration objects MUST be created to provide a single source of truth.
- **R-ENV-012** MUST: Environment variable validation at application startup using libraries like zod or envalid MUST be implemented to define schemas and fail fast on misconfiguration.
- **R-ENV-013** MUST: A .env.example file MUST exist in version control documenting all required and optional environment variables with example values and descriptions.

### Verify

```bash
# Count process.env usage
grep -r 'process\.env\.' --include='*.ts' --include='*.tsx' --include='*.js' --include='*.jsx' . | wc -l

# Check for hardcoded configuration values (URLs, API keys)
grep -r 'const.*=.*['"']http' --include='*.ts' --include='*.tsx' | grep -v process.env | grep -v '//.*http' | wc -l

# Verify .env.example exists
test -f .env.example && echo 'Configuration documentation exists' || echo 'Missing .env.example'
```

**Accept when:**
- All runtime configuration values are accessed via process.env rather than hardcoded strings or imported constants
- No hardcoded URLs, API keys, or environment-specific values appear in source code outside of test fixtures
- A .env.example file exists documenting all required environment variables with descriptions
- Environment variable validation is implemented at application startup using validation libraries
- A centralized configuration module exists that exports typed configuration objects

<enforcement>
Claude Code MUST verify all rules in this activation block. Violations of R-ENV-002 through R-ENV-006 and R-ENV-011 through R-ENV-013 are mandatory checks. Automated code review checks MUST scan for hardcoded configuration values. CI pipeline validation MUST ensure .env.example is kept up to date. Security scanning tools MUST flag potential credential exposure in code.
</enforcement>
