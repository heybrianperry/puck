<rule_activation id="d9c9c85b-530d-4db3-b715-1f2228bdefae" title="Standardize Environment Variable Access via process.env for Runtime Configuration: Environment Variable Access" applies_to="**/*">
These rules are ALWAYS ACTIVE for all runtime configuration and environment management implementations across the codebase.
</rule_activation>

### Rules

- **R-ENV-001** MUST: Environment variable access MUST occur at the module or function scope where the configuration is needed, not at global initialization unless explicitly required.

### Verify

```bash
# Count process.env usage across TypeScript and JavaScript files
grep -r 'process\.env\.' --include='*.ts' --include='*.tsx' --include='*.js' --include='*.jsx' . | wc -l

# Detect hardcoded URLs and environment-specific values not using process.env
grep -r 'const.*=.*['"']http' --include='*.ts' --include='*.tsx' | grep -v process.env | grep -v '//.*http' | wc -l

# Verify .env.example documentation exists
test -f .env.example && echo 'Configuration documentation exists' || echo 'Missing .env.example'
```

**Accept when:**
- All runtime configuration values are accessed via process.env rather than hardcoded strings or imported constants
- No hardcoded URLs, API keys, or environment-specific values appear in source code outside of test fixtures
- A .env.example file exists documenting all required environment variables with descriptions
- Server-side routes, data models, and utility functions consistently use process.env for accessing runtime configuration
- NEXT_PUBLIC_* prefixed environment variables in Next.js are used only for browser-exposed configuration with documented security implications

<enforcement>
Claude Code MUST verify all three bash commands pass before accepting changes. Violations detected by automated scanning tools (hardcoded configuration values, missing .env.example updates, credential exposure patterns) MUST be resolved or documented with tech lead approval and exception rationale in code comments.
</enforcement>
