<rule_activation id="2608f4bb-7172-4804-b002-1fae855d09a9" title="Standardize Environment Variable Access via process.env for Runtime Configuration: Sensitive Configuration Values" applies_to="**/*">
These rules are ALWAYS ACTIVE for all runtime configuration and environment management implementations across the codebase.
</rule_activation>

### Rules

- **R-ENV-001** MUST_NOT: Sensitive configuration values (API keys, secrets, credentials) MUST_NOT be committed to version control or included in client-side bundles.
- **R-ENV-002** MUST: All server-side runtime configuration (API endpoints, database URLs, service credentials) MUST be accessed via process.env.
- **R-ENV-003** MUST: Feature flags and environment-specific behavior toggles MUST be accessed via process.env.
- **R-ENV-004** MUST: Build-time configuration that varies across deployment targets MUST be accessed via process.env.
- **R-ENV-005** MUST: Third-party service integration parameters (API keys, webhook URLs) MUST be accessed via process.env.
- **R-ENV-006** MUST: Application-level settings (port numbers, timeouts, resource limits) MUST be accessed via process.env.
- **R-ENV-007** SHOULD: Create a centralized configuration module that reads from process.env and exports typed configuration objects.
- **R-ENV-008** SHOULD: Use .env.example files in version control to document all required and optional environment variables.
- **R-ENV-009** SHOULD: Implement environment variable validation at application startup using libraries like zod or envalid.
- **R-ENV-010** MAY: Client-side code in Next.js may access NEXT_PUBLIC_* prefixed environment variables that are explicitly intended for browser exposure (EXC-001).
- **R-ENV-011** MAY: Test environments may use hardcoded configuration values when testing configuration validation logic itself (EXC-002).

### Verify

```bash
# Count process.env usage across TypeScript and JavaScript files
grep -r 'process\.env\.' --include='*.ts' --include='*.tsx' --include='*.js' --include='*.jsx' . | wc -l

# Find hardcoded URLs not using process.env (excluding comments)
grep -r 'const.*=.*['"']http' --include='*.ts' --include='*.tsx' | grep -v process.env | grep -v '//.*http' | wc -l

# Verify .env.example documentation exists
test -f .env.example && echo 'Configuration documentation exists' || echo 'Missing .env.example'
```

**Accept when:**
- All runtime configuration values are accessed via process.env rather than hardcoded strings or imported constants
- No hardcoded URLs, API keys, or environment-specific values appear in source code outside of test fixtures
- A .env.example file exists documenting all required environment variables with descriptions
- Environment variable validation is implemented at application startup
- Sensitive variables are not logged or exposed in error messages

<enforcement>
Claude Code MUST verify all rules in this activation block. Violations of R-ENV-001 through R-ENV-006 are blocking. Automated scanning tools MUST flag hardcoded configuration values and credential exposure patterns. Pull requests modifying configuration MUST include .env.example updates.
</enforcement>
