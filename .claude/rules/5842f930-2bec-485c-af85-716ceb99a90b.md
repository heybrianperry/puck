<rule_activation id="5842f930-2bec-485c-af85-716ceb99a90b" title="Adopt Event-Driven Synchronization for State Management in Integration Boundaries: Components Event Driven" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching integration boundaries, components managing external state, API integration layers, and state management utilities that bridge subsystems.
</rule_activation>

### Rules

- **R-EVDS-001** MUST: Components using event-driven synchronization MUST handle edge cases such as race conditions, stale updates, and synchronization failures.

### Scope

**In scope:**
- Rich text editors and content management components that sync with external state
- Scripts and utilities that process event streams or changelog data
- API integration layers that coordinate between internal and external systems
- Components that manage bidirectional data flow across architectural boundaries
- State management utilities that bridge different subsystems or modules

**Out of scope:**
- Simple unidirectional data flow within a single component
- Direct function calls within the same module or service
- Synchronous API calls that don't require state synchronization
- Static configuration or initialization code
- Pure computational functions without external state dependencies

### Verify

```bash
# Identify event-driven synchronization patterns with hooks or event listeners
grep -r "use.*[Ss]ync" --include="*.ts" --include="*.tsx" --include="*.js" | grep -E "(hook|event|subscribe)"

# Count event listeners and subscriptions
grep -r "addEventListener\|on(.*\)\|subscribe" --include="*.ts" --include="*.tsx" --include="*.js" | wc -l

# Find files with event-sync patterns
find . -type f \( -name "*.ts" -o -name "*.tsx" -o -name "*.js" \) -exec grep -l "event.*sync\|sync.*event" {} \;
```

**Accept when:**
- Grep commands identify at least 2 files implementing event-driven synchronization patterns with hooks or event listeners
- Code review confirms that integration boundaries use event-driven patterns rather than direct synchronous coupling
- No new direct synchronous state coupling is introduced at integration boundaries without architectural review approval
- Proper event handling and state synchronization are verified through code review checklist
- Race condition handling, stale update management, and synchronization failure strategies are documented

### Implementation Guidance

- Create reusable hooks or utilities (e.g., use-synced-editor pattern) that encapsulate synchronization logic
- Use established patterns like Observer, Pub/Sub, or reactive programming libraries to standardize event handling
- Implement proper cleanup and unsubscription logic to prevent memory leaks in long-lived components
- Document the event flow and state reconciliation strategy for each integration point
- Use TypeScript types or interfaces to define event schemas and ensure type safety across boundaries

<enforcement>
Claude Code MUST verify event-driven synchronization compliance using the bash commands above. Violations at integration boundaries require architecture review approval. Direct synchronous coupling at documented integration boundaries triggers CI pipeline warnings and mandatory architecture review.
</enforcement>
