These rules are ALWAYS ACTIVE for all runtime configuration and environment management code. All configuration parameter handling MUST comply with the input validation rules defined herein.
</rule_activation>

### Rules

- **R-CFG-001** MUST_NOT: Configuration parameters MUST NOT be directly interpolated into system commands, database queries, or file paths without sanitization.
- **R-CFG-002** MUST: Validate all configuration parameters from external sources (environment variables, API requests, user input, file system operations) at the earliest possible point in the data flow.
- **R-CFG-003** MUST: Provide clear, actionable error messages that include the parameter name, received value, expected format, and valid range when validation fails.
- **R-CFG-004** SHOULD: Use schema validation libraries (Zod, Yup, Joi) to define configuration schemas declaratively and generate TypeScript types from schemas.
- **R-CFG-005** SHOULD: Cache validated configuration values to avoid repeated validation overhead, especially for environment variables that don't change during runtime.
- **R-CFG-006** SHOULD: Implement validation at initialization time rather than per-request for performance-critical scenarios.
- **R-CFG-007** MUST: Validate numeric parsing operations (parseInt, parseFloat, Number) with boundary checks or NaN/Infinity validation.
- **R-CFG-008** MUST: Log validation failures with appropriate severity levels to enable monitoring and alerting on configuration issues.

### Verify

```bash
# Check for unvalidated direct environment variable access
grep -r 'process\.env\[' --include='*.ts' --include='*.tsx' --include='*.js' | grep -v 'validate\|check\|parse' | wc -l

# Check for unvalidated numeric parsing operations
grep -r 'parseInt\|parseFloat\|Number(' --include='*.ts' --include='*.tsx' | grep -v 'isNaN\|isFinite\|>\|<\|throw' | head -20

# Run validation and configuration tests
npm test -- --grep 'validation|config' || echo 'No validation tests found'
```

**Accept when:**
- All direct accesses to process.env are wrapped in validation functions that check type and range
- Numeric parsing operations (parseInt, parseFloat, Number) are followed by boundary checks or NaN/Infinity validation
- Test suite includes validation test cases for configuration parameters covering valid, invalid, and edge case inputs
- Configuration parameters from environment variables, API requests, and file system sources are validated before use
- Validation failures produce clear error messages with parameter details and expected formats
- No unvalidated configuration parameters are interpolated into system commands, database queries, or file paths
