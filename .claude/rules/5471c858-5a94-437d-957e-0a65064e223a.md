<rule_activation id="5471c858-5a94-437d-957e-0a65064e223a" title="Adopt Browser-Based Rendering Model for E2E Testing Infrastructure: Test Utilities Provide" applies_to="**/*">
These rules are ALWAYS ACTIVE for E2E test utilities and browser-based rendering infrastructure.
</rule_activation>

### Rules

- **R-E2E-001** MAY: Test utilities MAY provide helper functions for common visual validation patterns such as element visibility and positioning.

### Verify

```bash
# Check for browser-native rendering APIs in E2E utilities
grep -r 'getBoundingClientRect\|getComputedStyle' scripts/e2e/utils/ --include='*.mjs' --include='*.js'

# Verify required utility modules exist
test -f scripts/e2e/utils/setup.mjs && test -f scripts/e2e/utils/get-box.mjs

# Run E2E test suite and verify passing tests
npm test -- --grep 'e2e' 2>&1 | grep -q 'passed' || echo 'E2E tests not found or failing'
```

**Accept when:**
- E2E utility modules exist in `scripts/e2e/utils/` and use browser-native rendering APIs (getBoundingClientRect, getComputedStyle, etc.)
- Test setup modules initialize browser contexts with consistent configurations before running tests
- E2E test suite passes successfully with rendering-based validations for UI element properties
- Helper functions for element visibility and positioning are centralized in shared utility modules
- Public API contracts are documented for rendering utility functions

<enforcement>
Claude Code MUST verify browser-based rendering model adoption through code review of E2E utilities, CI pipeline validation, and static analysis checks. Violations flagged in code review must be addressed before merge. Exceptions require QA Engineering lead approval with documented justification.
</enforcement>
