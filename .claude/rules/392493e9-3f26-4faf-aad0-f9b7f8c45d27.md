<rule_activation id="392493e9-3f26-4faf-aad0-f9b7f8c45d27" title="Adopt Modular Library Architecture with Core Package Pattern: Data Manipulation Utilities" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase to enforce modular library architecture with clear separation between core packages and application-specific code.
</rule_activation>

### Rules

- **R-MODLIB-001** MUST: Data manipulation utilities MUST be placed in `packages/core/lib` with clear, single-purpose module names (e.g., `flatten-data.ts`, `populate-ids.ts`).
- **R-MODLIB-002** MUST: All reusable utility functions and data transformation logic belong in core packages, not in application directories.
- **R-MODLIB-003** MUST: All reusable UI components intended for use across multiple features or applications belong in `packages/core/components`.
- **R-MODLIB-004** MUST: Custom React hooks that encapsulate reusable stateful logic belong in core packages.
- **R-MODLIB-005** MUST: Core packages MUST NOT import from application-specific directories (e.g., `recipes/`).
- **R-MODLIB-006** MUST: One-way dependency flow MUST be enforced: applications depend on core, never vice versa.
- **R-MODLIB-007** SHOULD: Server-side rendering implementations of core components SHOULD have corresponding `server.tsx` files.
- **R-MODLIB-008** SHOULD: Build and bundling configuration for library packages SHOULD be centralized in `packages/tsup-config/` or similar.
- **R-MODLIB-009** MAY: A component MAY be prototyped in an application directory before being promoted to core (EXC-001).
- **R-MODLIB-010** MAY: A utility function MAY have application-specific dependencies that cannot be abstracted (EXC-002).

### Out of Scope

The following MUST NOT be placed in core packages:
- Application-specific business logic and feature implementations
- Route handlers and API endpoints specific to individual applications
- Application-level configuration and environment-specific settings
- One-off components used in a single feature without reuse potential
- Test fixtures and mock data specific to individual test suites

### Verify

```bash
# Count utility modules in core/lib
find packages/core/lib -type f \( -name '*.ts' -o -name '*.tsx' \) | wc -l

# Count components in core/components
find packages/core/components -type f -name 'index.tsx' | wc -l

# Verify no application imports in core packages
grep -r 'from.*recipes/' packages/core/ && echo 'ERROR: Core package imports from application code' || echo 'OK: No application imports in core'

# Verify build config exists
test -f packages/tsup-config/react-import.js && echo 'OK: Build config exists' || echo 'ERROR: Missing build config'

# Detect circular dependencies
dependency-cruiser --validate .dependency-cruiser.js packages/core/ packages/ 2>/dev/null || echo 'Run dependency-cruiser to check for circular dependencies'
```

**Accept when:**
- Core package contains multiple utility modules in `lib` directory and multiple components in `components` directory
- No imports from application-specific directories (e.g., `recipes/`) are found in core package files
- Build configuration for library packages exists in a centralized location
- Components that require server-side rendering have corresponding `server.tsx` implementations
- Dependency analysis tools confirm no circular dependencies between core and application code
- Core packages can be built and tested independently without application code
