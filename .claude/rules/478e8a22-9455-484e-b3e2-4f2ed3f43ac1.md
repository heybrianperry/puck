<rule_activation id="478e8a22-9455-484e-b3e2-4f2ed3f43ac1" title="Adopt Explicit Export Pattern for Library Module Public APIs: Public Modules Not" applies_to="packages/core/lib/**/*.ts packages/core/lib/**/*.tsx packages/core/components/**/*.ts packages/core/components/**/*.tsx">
These rules are ALWAYS ACTIVE for all public API modules under packages/core/lib/ and packages/core/components/.
</rule_activation>

### Rules

- **R-EXPORT-001** MUST_NOT: Public API modules MUST NOT export internal helper functions, types, or constants unless explicitly intended for public use.
- **R-EXPORT-002** MUST: Use TypeScript's 'export type' for type-only exports to prevent runtime inclusion in bundles.
- **R-EXPORT-003** MUST: Establish naming conventions: index.tsx for component exports, descriptive names for utilities (e.g., flatten-data.ts, populate-ids.ts).
- **R-EXPORT-004** MUST: For server-specific modules, use .server.tsx extension and configure bundler to exclude from client builds.
- **R-EXPORT-005** SHOULD: Document public APIs in a centralized API reference, generated from TSDoc comments on exported members.
- **R-EXPORT-006** SHOULD: Consider using API Extractor or similar tools to generate API reports and detect unintentional breaking changes.

### Verify

```bash
# Count explicit export statements in public modules
grep -r 'export {' packages/core/lib packages/core/components | wc -l

# Find all index files (entry points)
find packages/core -name 'index.tsx' -o -name 'index.ts' | wc -l

# Run API Extractor to check public surface
npx api-extractor run --local || echo 'API surface check'

# Verify server-specific modules use correct naming
grep -r '\.server\.' packages/core/components | grep -v node_modules
```

**Accept when:**
- All public-facing modules under packages/core/lib and packages/core/components have explicit export statements
- No internal helper functions or private utilities are exported from public API modules
- Server-specific modules use .server.tsx extension and are not imported in client-side code
- Package.json exports field restricts access to only intended public modules
- API Extractor runs successfully without detecting unintended breaking changes
- No internal implementation details are exposed through public module exports

<enforcement>
Claude Code MUST verify all rules before accepting changes to public API modules. Verification is mandatory and MUST NOT be skipped or deferred. Build fails if API Extractor detects unintended breaking changes or if linter warnings indicate missing explicit exports in public directories.
</enforcement>
