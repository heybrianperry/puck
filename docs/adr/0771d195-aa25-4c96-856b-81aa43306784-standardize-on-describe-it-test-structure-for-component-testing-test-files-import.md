# Standardize on describe/it Test Structure for Component Testing: Test Files Import

Status: proposed
Date: 2024-01-09
Deciders: Detection Pipeline (automated)

## Context

- The codebase contains React component tests across multiple packages (core/components/Puck, core/components/ServerRender) that require consistent test structure and organization
- Testing infrastructure uses @testing-library/react and @testing-library/jest-dom for component rendering and assertions
- Tests cover both client-side component behavior (Puck richtext updates, root rendering) and server-side rendering scenarios (ServerRender RSC mode)
- The pattern emerged across 3 test files with 92.50% confidence, indicating established testing conventions
- Component tests need to verify both programmatic state updates via dispatch and DOM-based interactions with contentEditable elements

## Problem Statement

Without a standardized test structure using describe/it blocks, component tests become difficult to organize, maintain, and understand, particularly when testing complex scenarios involving state management, server-side rendering, and rich text editing capabilities across multiple packages.

## Decision

1. MUST: Test files MUST import @testing-library/jest-dom for DOM assertion matchers

## Policy Block

- MUST Test files MUST import @testing-library/jest-dom for DOM assertion matchers

In scope:
- Component test files in packages/core/components/**/__tests__/ directories
- React component unit and integration tests
- Tests verifying component rendering, state updates, and user interactions
- Server-side rendering (RSC) test scenarios

Out of scope:
- End-to-end tests using browser automation
- API or backend service tests
- Performance or load testing
- Visual regression tests

## Rationale

- The describe/it pattern provides clear test organization that scales across multiple component test files, as evidenced by consistent usage in Puck and ServerRender test suites
- @testing-library/react and @testing-library/jest-dom are established as the standard testing utilities across 3 detected files, providing consistent APIs for component testing
- The pattern supports diverse testing scenarios including programmatic updates via dispatch, contentEditable interactions, and server-side rendering verification
- Standardizing on this structure reduces cognitive load when navigating between test files and ensures consistent test output formatting

## Consequences

Positive:
- Improved test readability through hierarchical organization of test cases by component and feature
- Consistent test structure across packages enables easier onboarding and maintenance
- Clear test descriptions generated by describe/it blocks improve test failure diagnostics
- Established testing library ecosystem (@testing-library/react, jest-dom) provides robust component testing capabilities

Negative:
- Requires learning curve for developers unfamiliar with describe/it test structure
- Additional boilerplate compared to flat test file organization
- Potential for over-nesting with deeply hierarchical describe blocks
- Dependency on specific testing libraries (@testing-library/react) creates coupling to that ecosystem

## Alternatives

- Use flat test structure with test() functions instead of nested describe/it blocks (rejected)
  Rejected because: Flat structure does not scale well for component tests with multiple related scenarios, making it harder to organize tests by feature area or component hierarchy
  When valid: May be appropriate for simple utility function tests with few test cases
- Use Enzyme instead of @testing-library/react for component testing (rejected)
  Rejected because: Enzyme is no longer actively maintained and does not support React 18+ features; @testing-library/react encourages better testing practices focused on user behavior
  When valid: Only for legacy codebases still on React 16 or earlier
- Use Vitest instead of Jest as the test runner (deferred)
  Rejected because: Not rejected; Vitest is compatible with describe/it structure and could be adopted in the future
  When valid: When migrating to Vite-based build tooling or seeking faster test execution

## Risks

- Inconsistent test structure if developers are not aware of or do not follow the describe/it convention
  Mitigation: Add linting rules to enforce test structure patterns and include testing guidelines in documentation
  Owner: engineering team
- Over-reliance on @testing-library/react may make it difficult to test implementation details when necessary
  Mitigation: Document when and how to access component internals for legitimate testing needs while maintaining focus on user-facing behavior
  Owner: engineering team
- Test suite performance may degrade as number of describe/it blocks grows
  Mitigation: Monitor test execution times and use test.only/describe.only during development; consider test parallelization for CI
  Owner: engineering team

## Implementation Notes

- Place test files in __tests__ directories adjacent to the components they test, following the pattern packages/core/components/[Component]/__tests__/[test-file].spec.tsx
- Import testing utilities at the top of each test file: @testing-library/react for render/screen/fireEvent and @testing-library/jest-dom for matchers
- Structure tests with outer describe block named after the component, inner describe blocks for feature areas if needed, and it blocks for individual test cases
- For server-side rendering tests, import from react-dom/server.node and verify HTML output rather than using client-side rendering utilities

## Enforcement

- Verified by: Code review process checks for proper test structure in new test files
- Verified by: CI pipeline runs all tests and reports on test organization
- Verified by: Linting rules can be configured to enforce describe/it usage patterns
- Violation handling: Pull requests with improperly structured tests are flagged during code review
- Violation handling: Tests that do not follow the pattern are refactored before merge
- Violation handling: Documentation is updated to clarify test structure requirements
- Exception process: Exceptions may be granted for specialized test scenarios that require alternative structures
- Exception process: Exception requests must be documented in the test file with a comment explaining the rationale
- Exception process: Tech lead approval required for deviations from standard test structure
